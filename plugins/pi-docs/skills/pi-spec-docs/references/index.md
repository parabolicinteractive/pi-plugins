# Document Index

Path: `docs/README.md`

The entry point to the document set, for humans and for AI agents.

## Standing of This Document

Generated, not authored. Regenerate it with `/pi-docs index` after any structural
change, and automatically at every baseline. Never hand-edit it; edits are lost
on the next regeneration.

Like the glossary, this is a project convention rather than a standard-defined
information item. It exists because a directory containing seven document types
plus growing analysis and change directories is unnavigable without a map.

## What It Answers

Three questions, in this order:

1. **What is here, and what state is it in?** Every document, version, baseline,
   status, conformance.
2. **Where do I start?** A reading order for a newcomer, which differs by role.
3. **What must an agent respect?** The rules that stop an AI contributor from
   silently undoing the system.

It does not report findings. That is `/pi-docs-realign`. An index that also
diagnoses becomes stale the moment anything changes, and a stale diagnosis is
worse than none.

## The Agent Section Is the Point

Most of this file is a table anyone could reconstruct. The agent guidance is the
part that earns its place.

An AI contributor opening this repository months later has no memory of the
decisions, the vocabulary, or the traceability discipline. Left to itself it will
re-propose rejected approaches, invent synonyms for defined terms, edit an
accepted ADR, or add a requirement with no parent. Every one of those quietly
breaks something the package spent effort establishing.

The rules below are written as instructions to that agent, not as description.

## Where to Start

**Joining the project**: glossary, then StRS, then SRS. Read the ADR titles
before proposing anything architectural.

**Implementing a feature**: find the requirement in the SRS, follow its parent up
to the StRS for intent, follow its allocation down to the SAD and SDD.

**Testing**: STP section 11 maps every requirement to its coverage.

**Reviewing scope**: baseline records, then change requests carrying that
baseline.

## For AI Agents

These documents are authoritative. Follow these rules when working in this
repository.

1. **Read the glossary first.** Use its terms exactly. Never introduce a synonym
   for a defined term, and never use a term listed as rejected.

2. **Check the ADRs before proposing an approach.** A rejected ADR records an
   option already ruled out, with reasons. Re-proposing it wastes everyone's
   time. If you believe a decision should change, write a new ADR that supersedes
   the old one.

3. **Never edit an accepted ADR.** Only its status and supersession fields may
   change. The record of why something was decided keeps its value after the
   decision is reversed.

4. **Never renumber or reuse an identifier.** Requirements, decisions, views and
   design entities are cited across documents, tests, and code comments. A reused
   number turns every citation into a silent lie. A withdrawn item stays in place
   marked withdrawn.

5. **Cite requirement identifiers in code and commits.** When implementing, name
   the requirement being satisfied.

6. **Do not add a requirement without a parent.** Every functional and
   non-functional requirement derives from a stakeholder requirement, which
   derives from a source statement. A requirement with no parent is work nobody
   asked for.

7. **Do not silently drop anything from source material.** Every statement gets a
   disposition: requirement, finding, out of scope, or context. If it cannot be
   dispositioned, it becomes a finding.

8. **Update documents alongside code.** If a change invalidates a design or a
   decision, update the document in the same change, or raise a change request.

9. **Run `/pi-docs-realign` after structural changes** to catch what your change
   made stale elsewhere.

10. **Documents after a baseline change through change requests**, not direct
    edits. Check the current baseline in the state table above.
