# Specification Document System

A layered, cross-linked documentation architecture for software projects. Every document serves three audiences: the developer building the product, investors evaluating the opportunity, and AI agents assisting in construction.

## Document Taxonomy

The system organizes documents into four layers. Each layer builds on the ones above it.

### Layer 1 — Strategic & Business

These documents answer "why does this exist" and "who is it for."

- **Product Vision & Charter** (`docs/vision.md`) — Market opportunity, user segments, problem statement, value proposition, business model, success metrics. The entry point for investors. Updated quarterly or at major pivots.
- **Domain Model** (`docs/domain-model.md`) — Ubiquitous language glossary, core entities, bounded contexts, domain rules, domain events. The shared vocabulary contract. Updated whenever a new concept enters the system.

### Layer 2 — Requirements & Specification

These documents answer "what are we building" with testable precision.

- **Software Requirements Specification** (`docs/requirements.md`) — Functional and non-functional requirements, interface requirements, constraints, assumptions. Each requirement has an ID, acceptance criteria, and priority. Updated per feature cycle.
- **Executable Specifications** (`docs/specs/`) — BDD scenarios in Gherkin format (Given/When/Then) for critical user flows. These run as automated tests. One file per feature area. Updated alongside code.

### Layer 3 — Architecture & Decisions

These documents answer "how is it designed" and "why this approach."

- **Technical Architecture** (`docs/architecture.md`) — System design, component interactions, data flow, tech stack justification, deployment topology, scalability strategy. Updated when system boundaries change.
- **Architecture Decision Records** (`docs/adrs/`) — One file per significant decision. Numbered sequentially (`001-use-postgres.md`). Never deleted, only superseded. The most frequently created document type.
- **Requests for Comments** (`docs/rfcs/`) — Longer explorations of complex design problems before a decision is locked. Numbered sequentially. Status tracked in frontmatter. Lead to one or more ADRs.

### Layer 4 — Implementation & Operations

These documents answer "how do we build and run it."

- **Technical Design Specifications** (`docs/designs/`) — Per-feature design documents. Bridge architecture to implementation. One file per major feature or system component.
- **API Contracts** (`docs/api/`) — Interface specifications (OpenAPI, GraphQL schemas, webhook formats). Generated from code where possible, enriched manually.
- **Operations Guide** (`docs/operations.md`) — Deployment pipeline, monitoring strategy, incident response, rollback procedures, scaling runbooks.

### Cross-Cutting

- **Document Index** (`docs/INDEX.md`) — Master registry of all spec documents with status, last updated date, and cross-references. Auto-generated by the `/pi-doc-index` command.
- **README** (`docs/README.md`) — Entry point explaining the doc system itself. Points new contributors and AI agents to the right starting documents.

## Directory Structure Convention

```
project-root/
  docs/
    README.md              # Doc system entry point
    INDEX.md               # Auto-generated master index
    vision.md              # Product Vision & Charter
    domain-model.md        # Domain Model & Ubiquitous Language
    requirements.md        # Software Requirements Specification
    architecture.md        # Technical Architecture
    operations.md          # Operations & Deployment Guide
    adrs/                  # Architecture Decision Records
      _template.md         # ADR template
      001-example.md
    rfcs/                  # Requests for Comments
      _template.md         # RFC template
      001-example.md
    designs/               # Technical Design Specifications
      _template.md         # Design spec template
      feature-name.md
    specs/                 # Executable Specifications (BDD)
      feature-name.feature
    api/                   # API / Interface Contracts
      openapi.yaml
```

## Cross-Linking Rules

Documents form a directed graph, not a flat list. Follow these linking conventions:

1. **Requirements → Design Specs** — Every design spec references the requirement IDs it satisfies.
2. **Design Specs → ADRs** — Design specs link to ADRs that informed their approach.
3. **ADRs → RFCs** — ADRs link to the RFC that preceded them (if any).
4. **ADRs → Code** — ADRs reference the PR or commit where the decision was implemented.
5. **Design Specs → Executable Specs** — Design specs link to the BDD scenarios that verify them.
6. **Architecture → ADRs** — The architecture doc links to ADRs for each major technology choice.
7. **Domain Model → Everything** — All documents use terms as defined in the domain model. Inconsistencies are bugs.

Use markdown links with relative paths: `[ADR-001](adrs/001-use-postgres.md)`.

## Document Lifecycle

Every document has a status tracked in its YAML frontmatter:

- **Draft** — Work in progress. Not yet reviewed.
- **Review** — Ready for feedback. Circulating to stakeholders.
- **Accepted** — Approved and active. The current source of truth.
- **Superseded** — Replaced by a newer document. Links to successor.
- **Deprecated** — No longer relevant. Kept for historical context.

## Frontmatter Convention

All spec documents use YAML frontmatter for metadata:

```yaml
---
title: Document Title
status: accepted
created: 2026-01-15
updated: 2026-03-10
authors: [name]
tags: [relevant, categories]
links:
  - type: satisfies
    target: requirements.md#REQ-042
  - type: decided-by
    target: adrs/007-use-websockets.md
---
```

## When to Create Which Document

- "We need to decide between X and Y" → **ADR** (or RFC first if complex)
- "Here's a new feature to build" → **Design Spec** referencing requirement IDs
- "What does this term mean in our system?" → Update **Domain Model**
- "How does the whole system fit together?" → Update **Architecture**
- "A user should be able to do X" → **Requirement** in the SRS, then **Executable Spec**
- "Here's how to deploy/monitor/recover" → **Operations Guide**
- "What's our API surface?" → **API Contract**
- "Why does this project exist?" → **Product Vision & Charter**

## AI Agent Guidance

When an AI agent works on this project, it should:

1. **Read the domain model first** — learn the vocabulary before writing anything.
2. **Check ADRs before proposing alternatives** — the decision may already be made and documented.
3. **Reference requirement IDs** — when implementing features, cite the requirement being satisfied.
4. **Update docs alongside code** — if a code change invalidates a design spec or ADR, update the document in the same PR.
5. **Use the frontmatter** — status, links, and tags are machine-readable. Use them to navigate the doc graph.

For detailed templates for each document type, read the `pi-doc-templates` skill. For guidance on defining and enforcing domain vocabulary, read the `pi-domain-model` skill.
